# RumorBuster 线上答辩问答资料（成员 A）

> 答辩形式：老师提问，我们根据准备资料回答，不做项目主讲。
> 使用方法：先看目录判断问题属于哪一类，再用 `Ctrl+F` 搜关键词。回答时先读“简短回答”，老师继续追问时再看“可以补充”。

## 0. 答题方式

每个问题按这个顺序答：

1. 先用一两句话直接回答，不要先讲背景；
2. 老师继续问“为什么”时，再讲实现方法；
3. 老师问“代码在哪”时，再打开对应文件；
4. 不确定的实验结果要明确说“尚未完成”，不要猜数字。

建议线上答辩时提前打开：

- 本文档；
- `graph_v3.py`：系统主要流程；
- `evidence.py`：证据判断规则；
- `source_policy.py`：来源等级和时间检查；
- `evaluation/results/latest.json`：离线评测数字；
- `TEAM_CONTRIBUTIONS.md`：两人分工。

## 1. 项目和整体设计

### 1.1 这个项目是做什么的？

**简短回答**：RumorBuster 用来核验网上的文字或网页内容。它会查找公开资料，告诉用户哪些证据支持或反驳这句话，并给出可以点击查看的来源。

**可以补充**：用户可以直接输入文字、网页地址，也可以通过 Chrome 划词进入核验页面。结果包括主张、结论、采用的证据、没有采用的证据、原因和时间记录。

### 1.2 这个项目解决了普通大模型回答的什么问题？

**简短回答**：普通大模型可能凭已有知识回答，也可能给出不存在的链接。我们的系统要求结论必须和本次真正找到并读过的网页对应，证据不够就明确说证据不足。

**可以补充**：大模型仍然负责理解问题和整理语言，但最后的真假结果由代码中的固定规则计算，不能由模型随意修改。

### 1.3 为什么还要用大模型？全部写成规则不行吗？

**简短回答**：网上的表达方式很多，主张拆分、搜索词生成、网页内容理解很难全部写成固定规则。大模型适合处理这些语言问题，代码规则适合检查证据是否合格，两者分工更稳妥。

**可以补充**：大模型先给出候选结果，代码再检查链接、原文、来源等级、时间和独立性。可以理解为“大模型负责找和读，代码负责验和判”。

### 1.4 什么是 Agent？本项目里的 Agent 做什么？

**简短回答**：Agent 可以理解为一个能根据任务调用工具的大模型程序。本项目里的研究 Agent 会调用搜索和网页读取工具，整理候选证据，但不直接决定真假。

**可以补充**：普通网页研究员查公开网页，权威来源研究员查政府或专业机构，证据检查员只检查证据有没有缺口。

### 1.5 什么是 LangGraph？为什么使用它？

**简短回答**：LangGraph 是用图来组织大模型任务的框架。我们用它明确表示先做什么、哪些任务可以同时做、失败后走哪条路，以及最后怎样保存结果。

**可以补充**：它还负责保存同一会话的运行状态。相比让一个模型自由循环，流程图更容易检查、测试和展示。

### 1.6 DeerFlow 和 LangGraph 是什么关系？

**简短回答**：LangGraph 提供底层的流程运行能力；DeerFlow 在它上面提供模型配置、工具、子 Agent、会话文件和其他通用功能；RumorBuster 再在 DeerFlow 上增加谣言核验功能。

**可以补充**：我们没有从零重写通用框架，重点开发的是核验流程、RAG、来源检查、证据规则、时间记录、报告、API、前端和评测。

### 1.7 这个项目是不是 DeerFlow 套壳？

**简短回答**：不是简单换界面，但确实复用了 DeerFlow 和 LangGraph。复用的是通用框架，我们新增的是和谣言核验直接相关的流程与规则。

**可以补充**：例如“一条合格 A 类证据或两条独立 B 类证据”的判断、网页原文核对、来源职权检查、旧谣言检索和最终报告都不是 DeerFlow 原有功能。

### 1.8 哪些是框架原有的，哪些是你们做的？

**简短回答**：LangGraph 原有图运行和会话保存；DeerFlow 原有模型、工具、子 Agent 和 Sandbox。我们做了 RumorBuster 的主流程、证据处理、RAG、时间记录、网页与 API 展示和评测。

**代码位置**：

- 主流程：`packages/harness/deerflow/agents/rumor_agent/graph_v3.py`
- 证据规则：`packages/harness/deerflow/agents/rumor_agent/evidence.py`
- 来源检查：`packages/harness/deerflow/agents/rumor_agent/source_policy.py`
- RAG：`packages/harness/deerflow/agents/rumor_agent/rag.py`

## 2. 系统运行流程

### 2.1 一条消息进入系统后会发生什么？

**简短回答**：系统先判断用户是在聊天还是要求核验。如果是核验，就提取主张并判断现在能不能查，然后同时运行本地知识库检索、普通网页搜索、可选分类模型和权威来源搜索。最后统一检查证据，再由代码规则给出结果。

**顺序**：

```text
接收输入
→ 必要时读取用户给的网页
→ 提取和拆分主张
→ 判断能否公开核验
→ 同时查本地知识库、普通网页、权威来源和分类模型
→ 汇总并检查证据
→ 必要时再补查一次
→ 代码计算结论
→ 生成页面和报告
```

### 2.2 为什么要先判断“能不能核验”？

**简短回答**：不是所有句子都有可以公开查到的答案。例如个人喜好、隐私、还没发生的随机事件，都不应该硬判真假。

**可以补充**：提前判断可以减少无用搜索，也能避免系统为了给答案而编造证据。

### 2.3 为什么最多拆成三个子主张？

**简短回答**：一句话可能同时包含多个事实，只给一个总结果会掩盖其中一部分真、一部分假的情况。限制为最多三个，是为了兼顾核验完整性、运行时间和费用。

**可以补充**：每个重要子主张分别检查。若有的被支持、有的被反驳，整体可以判为“误导”；若重要子主张中有一个证据不足，整体不会强行下明确结论。

### 2.4 V2 和 V3 有什么区别？

**简短回答**：V2 主要让模型按阶段调用工具，流程较依赖模型是否按要求执行。V3 把步骤写成明确的图，哪些任务同时执行、失败后怎么办都在代码里规定，更容易检查和测试。

**可以补充**：V2 仍保留为回退版本，图的名字是 `rumor_agent_v2`；当前默认使用 V3，也就是 `rumor_agent`。

### 2.5 系统哪些任务是同时执行的？

**简短回答**：本地知识库检索、普通网页研究、分类模型、权威来源研究和可选的时间记录研究可以同时开始。全部返回后，系统再统一检查证据。

**可以补充**：代码使用 LangGraph 的 `Send` 启动这些任务，每个任务记录开始和结束时间。多个时间区间重叠，可以证明不是按顺序一个个执行。

**代码位置**：`graph_v3.py` 中的 `make_parallel_sends`、`merge_branch_status` 和 `build_rumor_graph_v3`。

### 2.6 为什么一定要等所有任务结束后再判断？

**简短回答**：如果只看到其中一个任务的结果就判断，可能漏掉另一边的反对证据。统一收齐后再判断，结论才基于完整的本轮结果。

### 2.7 `thread_id` 和 `run_id` 有什么区别？

**简短回答**：`thread_id` 代表一整个聊天会话；`run_id` 代表这个会话中的一次新核验。聊天历史可以保留，但每次核验的证据必须重新开始。

**可以补充**：这样既能继续多轮对话，又能防止上一轮找到的网页被误用到下一轮。

### 2.8 如果某一个搜索任务失败，整个流程会失败吗？

**简短回答**：不会。每个任务单独记录成功、跳过或不可用，其他任务仍可继续。最后如果合格证据不够，系统输出“证据不足”，而不是编一个结果。

### 2.9 普通研究员和权威研究员有什么区别？

**简短回答**：普通研究员面向整个公开网络；权威研究员只在医学、法律、金融、政策、科学等领域启用，并优先搜索事先登记的官方或专业网站。

**当前限制**：

- 普通研究员：搜索 1 次，最多读取 3 个网页，最长 55 秒；
- 权威研究员：搜索 1 次，最多读取 2 个网页，最长 55 秒；
- 证据检查员：没有搜索工具，最长 20 秒；
- 补查：最多发生一次，搜索 1 次，读取最多 2 个网页，最长 35 秒。

### 2.10 工具次数只是写在提示词里吗？

**简短回答**：不是。当前代码会给搜索和网页读取工具加计数限制，超过次数后工具不会继续执行，只返回已经达到上限的错误信息。总对话轮数和运行时间也有限制。

**代码位置**：`packages/harness/deerflow/subagents/executor.py` 中的 `_wrap_tool_with_call_budget`。

## 3. 证据和最终结果

### 3.1 什么样的网页才能用于最终判断？

**简短回答**：必须是本次运行真正搜索到的链接，网页读取成功，引用的原句能在网页正文中找到，而且来源、时间和内容都与当前主张相符。

**不能直接采用的情况**：

- 只有搜索结果摘要，没有读取正文；
- 链接只出现在模型回答里，没有出现在工具结果里；
- 引用句无法在网页正文中找到；
- 网页与主张关系不直接；
- 来源太弱、时间不合适，或者只是同一篇文章的转载。

### 3.2 A、B、C、D 四类来源是什么意思？

**简短回答**：A 是对这件事有直接职责的官方来源；B 是专业机构、学术机构、正规媒体，或者官方但职责没有完全匹配的来源；C 是普通网页或只有搜索摘要；D 是个人或来源不明的内容。

**重点**：只有符合其他条件的 A、B 能进入最终判断；C、D 可以作为线索，但不能凑数量。

### 3.3 官方网站一定是 A 类吗？

**简短回答**：不一定。网站是官方的，还要看这个机构是否负责当前事情。例如气候问题可以看 NASA 或 IPCC，但它们不能因为是官方机构就自动证明所有领域的主张。

**可以补充**：代码会根据登记的机构、网站和职责关键词检查。没有匹配职责的官方网站最多按 B 类处理。

### 3.4 最终结论是怎样算出来的？

**简短回答**：支持或反驳一方有一条合格 A 类证据，或者两条互相独立的 B 类证据，才能给出明确结果。达不到就说证据不足。

**四种常见情况**：

| 证据情况 | 结果 |
|---|---|
| 一条合格 A 支持主张 | 非谣言，高证据强度 |
| 两条独立 B 反驳主张 | 谣言，中等证据强度 |
| 两条 B 实际转载同一篇稿件 | 仍然证据不足 |
| 支持和反驳双方各有合格 A | 存疑，不让模型自己选一边 |

### 3.5 为什么规定“一条 A 或两条 B”？

**简短回答**：这是课程版本为了让判断过程清楚、可重复而采用的保守规则。A 类来源对相关事项有直接职责；B 类来源没有同样强的职责保证，所以要求两个独立来源互相印证。

**不要夸大**：这不是所有事实核查机构通用的唯一标准，而是本项目选择的一套可以解释和测试的规则。

### 3.6 怎样判断两个来源是否独立？

**简短回答**：代码会比较网站域名、发布者和文章内容。相同网站、相同发布者或内容高度相似的转载，会归为同一组，只算一个来源。

### 3.7 如果 A 类证据和 B 类证据相反，听谁的？

**简短回答**：一条合格 A 会优先于相反方向的 B、C、D。如果双方都有合格 A，就输出存疑，不让大模型选择自己更相信的一方。

### 3.8 怎样防止大模型编造链接？

**简短回答**：系统不相信模型最后一段文字里自己写出的链接，只接受搜索或网页读取工具在本次运行中真实返回过的链接。

**可以补充**：报告生成前还会再检查一次，把没有真实出现过的链接删除。

### 3.9 怎样防止大模型编造网页原句？

**简短回答**：读取网页后，系统保存正文的校验值，并检查引用是否是正文中连续出现的原文。找不到的引用不能作为直接证据。

**可以补充**：若模型找到候选网页但没有正确读取或摘录，系统最多会自动重新读取两个候选网页，并由代码从正文中选择原句。

### 3.10 为什么用户提供的原网页不能证明自己？

**简短回答**：用户给的网页只是“被核验对象”，它只能说明原文写了什么，不能独立证明原文是真的。系统还必须寻找其他来源。

### 3.11 为什么“没搜到”不能证明是假的？

**简短回答**：没搜到可能是搜索范围、网页下线或网络问题，不等于事情没有发生。所以系统不会把“没有结果”当成反驳证据，只会说证据不足。

### 3.12 时间因素怎样处理？

**简短回答**：系统先判断主张是在说当前情况、历史事件还是一般事实。带“目前、最新、当前”等词的主张要特别检查资料是否过旧；历史事件可以使用当年的档案；像“吸烟有害健康”这种一般事实不会简单因为资料超过一年就淘汰。

## 4. RAG 和 LoRA

### 4.1 什么是 RAG？

**简短回答**：RAG 是先从资料库找出与问题相关的内容，再把这些内容交给大模型参考。本项目用它查找已经人工复核过的旧谣言和资料。

**重点**：RAG 找到“相似旧案例”不等于当前主张已经被证明，旧案例中的来源需要重新读取和检查后才能用于最终判断。

### 4.2 本项目的 RAG 是怎样实现的？

**简短回答**：系统同时使用语义相似搜索和关键词搜索，再把两边的排名合并。语义搜索使用 HuggingFace 向量模型和 Chroma；关键词搜索使用 TF-IDF。

**通俗解释**：

- 语义搜索能找到“意思接近、用词不同”的内容；
- 关键词搜索更擅长人名、数字和固定短语；
- 两种结果合并，可以互相补足。

### 4.3 为什么需要两种检索方式？

**简短回答**：只看关键词容易漏掉换一种说法的旧谣言，只看语义也可能在数字和专有名词上不够准确。两种方式一起用更稳。

### 4.4 如果向量模型或 Chroma 不可用怎么办？

**简短回答**：系统退回关键词检索，不会在用户请求时临时下载模型或重建索引。如果两种检索都不可用，仍然可以继续进行网页核验。

### 4.5 什么是 LoRA？为什么使用 LoRA？

**简短回答**：LoRA 是一种只训练少量附加参数的模型微调方法，不需要重新训练整个大模型，显存和训练成本更低。我们用它让 Qwen2.5-3B 更适应谣言分类任务。

### 4.6 LoRA 模型在系统中负责什么？

**简短回答**：它只根据文字给出谣言、非谣言或不确定的辅助标签，不读取本轮网页证据，也不能决定最终结果。

**可以补充**：系统会显示 LoRA 标签与证据结论是一致、冲突还是无法比较，方便分析模型表现。

### 4.7 LoRA 模型输出异常怎么办？

**简短回答**：系统只精确接受 `Yes`、`No`、`Unknown`。超时、非法内容或没有配置服务时统一按“不确定或不可用”处理，不会默认成“非谣言”。

### 4.8 LoRA 训练和接入是谁负责的？

**简短回答**：成员 A 使用 LLaMA-Factory 完成 LoRA 训练和数据处理；成员 B 主要负责把模型服务接入 RumorBuster，包括两种接口适配、标签转换和异常处理。

### 4.9 微调后的 3B 模型测试结果是多少？

**简短回答**：微调后的 Qwen2.5-3B 模型在 1940 条三分类测试集上的总体准确率是 90.00%，Macro F1 是 0.89，Weighted F1 是 0.90。

| 标签 | 含义 | Precision | Recall | F1 | 数量 |
|---|---|---:|---:|---:|---:|
| `No` | 非谣言 | 0.84 | 0.91 | 0.88 | 710 |
| `Unknown` | 不确定 | 0.92 | 0.78 | 0.84 | 464 |
| `Yes` | 谣言 | 0.95 | 0.96 | 0.95 | 766 |

**可以补充**：`Yes` 类表现最好；`Unknown` 类召回率只有 0.78，说明模型对“不确定”样本更容易漏判，这是需要继续改进的地方。

### 4.10 这个 90% 是 RumorBuster 整套系统的准确率吗？

**简短回答**：不是。这是 3B 微调模型单独做文本三分类的离线准确率，不包含联网搜索、网页读取、来源检查和最终证据判断。

**可以补充**：模型成绩证明 LoRA 训练有效，但模型在系统里仍只是辅助判断。RumorBuster 的真实效果要看另外的联网验收，不能把两个数字混在一起。

## 5. 时间记录、会话、前端和 API

### 5.1 系统能找到谣言最早的源头吗？

**简短回答**：不能保证。系统只能列出本次搜索中找到的较早公开网页，所以页面写的是“本轮最早检索记录”，不是绝对源头。

**可以补充**：网页可能被删除、没有被搜索引擎收录，或者更早在线下传播。因此这些记录只用来展示说法随时间的变化，不参与真假判断。

### 5.2 为什么至少需要三个时间记录？

**简短回答**：一两个网页不足以展示变化过程。至少三个不同日期、能够读取正文的记录，才会显示为较完整的时间记录；否则页面明确提示资料不足。

### 5.3 Checkpointer 是什么？

**简短回答**：它负责保存每个会话的消息和流程状态，让用户刷新或继续对话时还能恢复之前的内容。当前课程版本使用 SQLite。

### 5.4 Memory 和 Checkpointer 有什么区别？

**简短回答**：Checkpointer 保存具体会话和流程；Memory 保存跨会话的用户偏好。Memory 只能影响回答方式，不能当成事实来源，也不能改变核验结论。

### 5.5 Sandbox 在项目中做什么？

**简短回答**：Sandbox 用于限制文件和命令操作的范围。V3 的核心核验过程主要调用搜索、网页读取、RAG 和分类服务，不依赖 Sandbox 来判断真假。

### 5.6 前端怎样拿到结果？

**简短回答**：前端使用 LangGraph 的客户端按流式方式接收运行状态。运行中显示当前步骤和各任务状态，结束后直接读取 `rumor_report` 数据并显示证据卡片，不需要从大模型文字里重新猜结论。

**代码位置**：`frontend/src/core/threads/hooks.ts`、`frontend/src/components/workspace/messages/rumor-report-card.tsx`。

### 5.7 Gateway API 有什么作用？

**简短回答**：Gateway 给脚本或其他程序提供统一的 HTTP 接口。它负责创建 LangGraph 会话、等待或查询运行结果，再把流程状态和报告返回给调用方。

**接口**：`POST /api/v1/checks` 创建核验，`GET /api/v1/checks/{check_id}` 查询结果。

## 6. 测试、分工和不足

### 6.1 40 条评测和 127 项测试分别是什么？

**简短回答**：40 条是固定的离线功能检查，覆盖能否核验、RAG、证据规则、多个子主张和失败处理；127 项是 8 月 17 日留档的定向代码测试。它们都不是 40 次或 127 次真实联网核验。

**可以补充**：40 条离线检查当前各类指标为 1.0，只能说明这些预先设计的功能场景都通过，不能代表系统面对所有网络信息的总体准确率。

### 6.2 现在最新测试是全部通过吗？

**简短回答**：不是。8 月 22 日重跑当前选择集是 178 项通过、2 项失败。两个失败都是旧测试仍在检查旧配置：一个期待 DuckDuckGo，另一个期待普通研究员读取 4 个网页；当前实现已经改成 Tavily 和最多 3 个网页。

**回答原则**：可以说核心流程和规则相关测试通过，但不能说当前最新选择集全部通过。

**如果老师问为什么没有修**：这是提交收口时测试没有同步，是我们的疏漏。它不是运行算法报错，但仍然属于测试失败；正确处理是把两条测试改成当前配置，再完整重跑，而不是忽略失败。

### 6.3 为什么离线指标是 1.0，能说明系统很准确吗？

**简短回答**：不能直接说明真实世界总体准确。因为这些是固定的功能样本，主要用来检查代码修改后是否破坏已定义规则。

**可以补充**：删除时间检查后准确率降到 0.8333，删除来源独立性检查后降到 0.9444，说明这两部分规则确实影响结果；但样本规模仍然有限。

### 6.4 真实联网做过什么验证？

**简短回答**：项目保存了若干真实网页运行结果。“抽烟有害身体健康”连续两轮都得到非谣言、高证据强度结果，分别由国家卫健委和 WHO 的 A 类证据支持。

**不要夸大**：三个固定真实案例各运行两次、模型服务接入后的整套联网验收都还没有完成。1940 条的 90% 是模型离线分类结果，不是系统联网准确率。

### 6.5 你本人主要做了什么？

**简短回答**：我主要负责 V3 后端流程、证据判断规则、来源检查、RAG、网页搜索与读取改造、统一核验 API、部署和评测框架，也负责 LoRA 模型训练和数据处理。

### 6.6 队友主要做了什么？

**简短回答**：队友主要负责 LoRA 模型服务接入和调试、子 Agent 运行稳定性、证据数据到前端的衔接、部分测试维护、真实验收执行和答辩材料整理。

### 6.7 为什么贡献比例是 6:4？

**简短回答**：比例依据工作日志、Git 提交和实际交付物综合估算。成员 A 承担主要后端架构和模型训练，成员 B 承担模型接入、稳定性、前端衔接和验收材料，因此约为 6:4。

### 6.8 项目目前最大的不足是什么？

**简短回答**：第一，3B 模型已经有离线测试成绩，但接入系统后的完整联网验收还不够；第二，真实联网案例数量仍然较少，而且搜索结果会变化；第三，A/B 规则和来源登记表还需要更多真实数据验证和调整。

### 6.9 如果再给一周，最先做什么？

**简短回答**：先修正两个没有同步的测试，再完成模型服务接入后的冒烟测试和三个真实案例双跑，把结果、失败案例和运行环境保存下来。当前最需要补的不是更多功能，而是完整、可重复的验收材料。
